## 2. 选题背景与研究意义

高校课程设计、协作开发和日常学习场景中，电子文件的存储、共享与预览需求持续增加。本地文件夹和个人云盘在多人协作、长期归档、环境复现方面存在不足，容易出现文件分散、版本混乱、预览受限、部署环境不一致等问题。

传统 Web 系统在部署时通常依赖本机环境、数据库初始化、静态资源路径、文件目录权限等配置。一旦换到新的电脑或答辩演示环境，重新搭建和排错会消耗较多时间。对于毕业设计答辩而言，系统不仅要实现功能，还要能快速恢复运行状态并稳定演示。

容器化部署为本课题提供了工程支撑。Docker 与 Docker Compose 可以把前端、后端、数据库、缓存和反向代理等组件写入统一编排文件，通过镜像和数据卷降低环境差异。配合本地目录持久化后，开发、测试和答辩演示可以使用相对一致的运行环境。

研究意义可以概括为三点：

- 工程实践意义：把文件管理系统从单点功能实现推进到可运行、可复现、可演示的完整工程。
- 教学答辩意义：围绕文件上传、下载、预览、分享、回收、用户隔离等核心功能形成清晰演示链路。
- 技术应用意义：验证前后端分离、关系型数据库、缓存、反向代理和 Docker Compose 在轻量级云文件管理系统中的组合应用。

## 3. 国内外研究现状与课题切入点

国外云文件管理与云存储产品发展较早。Dropbox、Google Drive、OneDrive 等商业系统在文件同步、在线预览、链接分享和权限控制方面已较成熟；Nextcloud、Seafile 等开源方案在私有化部署、存储自主可控和二次扩展方面具有代表性。相关研究关注分布式存储一致性、签名 URL、访问控制、容器化部署及云原生运维等方向。

国内云存储实践主要由阿里云 OSS、腾讯云 COS、华为云 OBS 等对象存储服务支撑，企业网盘、内容分发、多媒体平台等场景应用较多。学术与工程实践中较常见的方向包括 Docker/Kubernetes 在中小型 Web 系统中的应用、Office 文档与图片视频预览转码、SaaS 和多租户场景下的权限隔离等。

本课题不与成熟商业网盘或大型对象存储平台竞争，而是收敛到本科毕业设计场景中的三个切入点：

- 环境快速复现：解决答辩演示时依赖多、配置复杂、迁移困难的问题。
- 预览访问链路：在 Nginx 反向代理、路径归一化、签名校验和本地文件读取之间保持一致。
- 轻量用户隔离：通过 admin/demo 两类账号和 `lfs_file.user_id` 字段实现与课题边界匹配的用户视角隔离。

## 5. 技术路线

系统采用前后端分离架构和容器化部署路线。

技术栈概括：

- 前端：Vue 3、Element Plus、Vite、Vue Router。
- 后端：Spring Boot 3.2.2、MyBatis-Plus 3.5.5、JWT、BCrypt。
- 数据层：MySQL 8、Redis 7。
- 部署层：Nginx、Docker、Docker Compose。
- 文件处理与预览：Aspose、PDFBox、JAVE、本地签名访问。

技术路线表达建议：

需求分析 -> 系统概要设计 -> 数据库与接口设计 -> 核心模块实现 -> Docker Compose 容器化部署 -> 功能测试、异常测试与自动化测试验证。

选型理由提炼：

- Vue 3 与 Element Plus 适合构建文件列表、弹窗、上传进度、分享面板和回收站等后台管理类交互。
- Spring Boot 便于快速搭建 REST 接口，MyBatis-Plus 能减少文件元数据 CRUD 的重复代码。
- MySQL 用于保存用户、文件、分享、回收站等结构化数据；Redis 用于上传分片状态、转码进度等短生命周期数据。
- Nginx 统一静态资源入口、业务接口代理和文件预览访问入口。
- Docker Compose 将前端入口、后端服务、数据库和缓存统一编排，降低演示环境复现成本。

## 6. 系统总体设计

系统按前后端分离 B/S 形态设计，从上到下可拆为四层：

- 表现层：由 Vue 3、Element Plus、Vite 和 Vue Router 构建，包括登录页、文件管理页、分享访问页、回收站页、预览页等。
- 业务层：由 Spring Boot 提供登录认证、文件管理、目录管理、预览、分享、回收站和存储统计等接口。
- 数据与资源层：MySQL 保存结构化元数据，Redis 保存短生命周期状态，本地持久化目录保存上传文件。
- 部署与代理层：Nginx 提供统一访问入口，Docker Compose 编排四个核心容器。

总体架构说明：

浏览器访问 Nginx，Nginx 一方面返回前端静态资源，另一方面将 `/api/**` 业务请求、预览资源请求转发给后端。后端负责业务处理、权限识别、签名校验和文件读写；MySQL 存储元数据，Redis 维护临时状态，本地目录保存物理文件。

## 7. 功能模块设计

核心功能模块：

- 用户认证模块：登录鉴权、token 解析、当前用户识别；依赖 `sys_user`、JWT 工具类、`CurrentUserService`。
- 文件管理模块：文件上传、列表、目录、重命名、移动、删除；依赖 `lfs_file`、`FileMapper`、MyBatis-Plus。
- 预览模块：原文件预览、缩略图预览、转码文件访问；依赖 `FilePreviewController`、签名校验和本地资源目录。
- 分享模块：分享码生成、有效期校验、匿名访问；依赖 `lfs_file_share` 和 `FileShareServiceImpl`。
- 回收站模块：删除、恢复、彻底删除、清空；依赖 `lfs_file_trash` 与 `lfs_file_trash_detail`。
- 存储统计模块：按用户维度统计空间使用量；依赖 `lfs_file.user_id` 与统计 SQL。
- 兼容补丁模块：启动期字段、索引与演示账号自动补齐；依赖 `SchemaCompatibilityRunner` 和 JDBC Template。

模块协作逻辑：

用户请求受保护接口时，认证模块先从请求头解析 JWT，得到当前用户 ID 和是否为管理员的信息。文件管理、回收站、分享和统计模块在查询时通过 `CurrentUserService` 获取当前用户，并将归属条件追加到 SQL 查询中。预览和分享模块生成访问 URL 时使用 `secret` 与 `expire`，访问资源时由后端统一校验。

## 8. 数据库设计

数据库设计以 `lfs_file` 为核心。论文中明确提到的核心表包括：

- `sys_user`：保存用户账号、密码、角色等信息。
- `lfs_file`：保存文件和目录的元数据，是文件管理业务核心表。
- `lfs_file_share`：保存分享码、过期时间、访问次数等分享信息。
- `lfs_file_trash`：保存回收站删除批次和删除记录。
- `lfs_file_trash_detail`：保存回收站明细，与文件记录形成关联。
- `lfs_file_thum`：保存缩略图相关信息。

核心字段：

- `lfs_file.user_id` 是双用户隔离的核心字段，用于标识文件记录归属。
- `idx_user_id` 是 `user_id` 字段上的辅助索引，用于支持按用户过滤查询。
- `lfs_file.id` 被分享、回收站、缩略图等表引用，形成以文件表为中心的关系结构。

数据库兼容性设计：

考虑到答辩演示环境可能复用旧 MySQL 数据卷，系统启动时由 `SchemaCompatibilityRunner` 检查 `lfs_file.user_id` 字段、`idx_user_id` 索引和 demo 演示账号是否存在。如缺失，则自动补齐。该过程设计为幂等执行，避免重复启动破坏已有数据。

## 9. 核心功能实现

### 9.1 用户认证与权限边界

系统保留 admin 和 demo 两类账号。admin 表示管理员视角，可查看和管理全量文件数据；demo 表示普通演示用户，仅能访问自身文件空间。登录后后端签发 JWT，前端保存并在后续请求中携带 token。后端通过 `CurrentUserService` 统一解析当前用户 ID 和管理员身份，避免各业务模块重复解析 token。

答辩表达重点：

- 认证模块是其它业务模块的前置依赖。
- 用户隔离不是靠前端隐藏按钮，而是通过后端当前用户解析和 SQL 条件共同保证。

### 9.2 文件上传、列表与目录管理

文件管理模块负责上传、列表、目录、移动、重命名和删除。上传过程需要保存物理文件，同时在 `lfs_file` 中写入文件元数据。目录树由前端 `el-tree` 渲染，后端按层级返回 `is_dir = 1` 的记录。移动文件主要修改 `parent_id`；命名冲突由前端预校验和后端同目录同名检查共同处理。

### 9.3 双用户隔离

隔离机制依赖两层：

- 身份识别：`CurrentUserService` 提供当前用户 ID 和 `isAdmin` 标记。
- 查询过滤：管理员查询时不追加 `user_id` 限制；demo 用户查询时追加 `user_id = currentUserId`，只命中自身文件。

该机制覆盖文件列表、回收站、存储统计等视角。论文测试中 admin 和 demo 在文件列表、回收站记录、存储统计上的视角差异与设计预期一致。

### 9.4 文件预览与分享访问

预览模块负责原文件预览、缩略图预览和转码资源访问，对应路径包括 `/api/files/`、`/api/thum/`、`/api/trans/**`。这些路径经 Nginx 转发后进入 `FilePreviewController`，由控制器进行路径归一化、`secret + expire` 签名校验、文件越界检查和响应头设置。

收尾阶段修复了两类问题：

- 路径前缀错位导致的 404，由 `normalizeRequestPath` 统一处理。
- 中文或空格路径在签名生成和校验中编码不一致导致的 `secret` 校验失败，由统一 URL 解码与再编码规则处理。

分享模块采用“分享码 + 有效期 + 匿名访问”方式。分享访问不扩展为复杂协作权限系统，符合轻量级演示系统边界。

### 9.5 回收站与存储统计

回收站模块支持文件删除、恢复、彻底删除和清空。删除后文件进入回收站，恢复时回写原 `parent_id`，彻底删除时同步清理物理文件。回收站、文件列表和存储统计共享同一套用户视角，避免出现列表不可见但统计计入空间的矛盾。

存储统计按 `user_id` 维度聚合空间使用情况。管理员查看全量统计，demo 仅查看自身统计。统计 SQL 显式过滤 `in_trash = 0`、`deleted = 0`、`is_dir = 0`，并使用 `COALESCE` 处理无文件场景。

### 9.6 容器化部署

系统通过 Docker Compose 编排四个核心容器：

| 容器 | 镜像基础 | 主要职责 | 对外端口 |
|---|---|---|---|
| lfs-nginx | nginx:alpine | 统一入口与反向代理 | 80 |
| lfs-backend | 自构建 OpenJDK 17 | Spring Boot 业务接口 | 内部 8919 |
| lfs-mysql | mysql:8.0 | 业务数据持久化 | 内部 3306 |
| lfs-redis | redis:7-alpine | 临时状态与上传分片标识 | 内部 6379 |

部署启动流程：

1. 执行 `docker compose up -d --build`。
2. Compose 校验服务定义、网络与数据卷映射。
3. 按依赖顺序启动 MySQL、Redis、Backend、Nginx。
4. MySQL 健康检查通过后，后端启动。
5. `SchemaCompatibilityRunner` 自动补齐字段、索引、演示账号。
6. 浏览器通过 Nginx 入口访问系统。

## 12. 总结、不足与展望

已完成工作：

- 完成前端、后端、数据层、反向代理与容器编排的完整系统架构。
- 实现登录认证、文件上传、目录管理、文件预览、分享访问、回收站、存储统计等核心业务闭环。
- 通过 `lfs_file.user_id`、`CurrentUserService` 和 SQL 条件拼接实现轻量级双用户隔离。
- 通过 `FilePreviewController.normalizeRequestPath` 和 `secret + expire` 签名校验统一预览访问链路。
- 通过 Docker Compose 编排四个容器，并使用本地目录持久化提高演示环境复现能力。
- 通过功能测试、异常测试、自动化测试和运行观察验证主要功能。

不足：

- 当前系统仍是轻量级毕业设计演示系统，没有扩展为完整多租户协作平台。
- 用户权限模型较简单，仅保留 admin/demo 两类视角，没有实现复杂 RBAC、团队空间、共享文件夹等能力。
- 文件存储采用本地目录持久化，未扩展到对象存储或分布式存储。
- 系统监控、日志分析、自动化运维和容量管理能力还较基础。
- 文件预览与转码能力覆盖常见类型，但仍可进一步扩展格式兼容性与缓存策略。

展望：

- 引入更细粒度权限控制，支持团队空间、共享文件夹和协作权限。
- 扩展对象存储支持，提高存储弹性和迁移能力。
- 完善分享策略，如访问次数限制、密码访问、操作审计等。
- 增强系统监控、日志分析和自动化部署能力。
- 优化预览转码缓存，提高多格式文件访问体验。

## 13. PPT 视觉风格建议

答辩场景要求正式、清晰、学术、简洁，避免商业路演风格。

推荐视觉方案：

- 主色调：深蓝 + 白色 + 浅灰，少量青蓝作为强调色。
- 背景：以白色或极浅蓝灰为主，关键章节页可使用深蓝背景。
- 字体：中文使用微软雅黑或思源黑体风格，英文和代码使用 Arial/Consolas 风格。
- 排版：一页一个核心结论，使用短句、表格、流程图和架构图替代大段文字。
- 图表：结构图、流程图、E-R 图统一采用蓝灰学术风，扁平化、低装饰、留白充足。
- 截图：真实系统截图应加统一边框、标题标签和必要的局部标注，避免过度美化导致真实性下降。
- 页脚：可统一设置论文题目缩写、页码和答辩场景信息。
