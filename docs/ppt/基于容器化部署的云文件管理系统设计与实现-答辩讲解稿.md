# 《基于容器化部署的云文件管理系统设计与实现》答辩讲解稿

> 建议时长：8-10 分钟。讲解原则：本科毕业设计答辩口径，突出真实实现、容器化部署、核心功能和运行效果，不做商业路演式夸大。

## 1. 封面

各位老师好，我是网络工程 2203 班的杨佳星。我的论文题目是《基于容器化部署的云文件管理系统设计与实现》。一句话概括这个课题，就是用 Spring Boot 和 Vue 3 做一个真实可运行的云文件管理系统，再用 Docker Compose 把前端入口、后端服务、数据库和缓存统一部署起来。下面我会重点讲三个问题：系统为什么要做，系统怎么设计和部署，以及最后实际跑出来的功能效果。

## 2. 目录

接下来我按四个部分汇报。第一部分是背景和目标，说明这个系统解决什么问题；第二部分是系统设计和容器化部署，重点讲架构和容器之间的关系；第三部分是核心功能实现，包括文件管理、预览分享、用户隔离和回收站；最后是测试验证、系统界面展示和总结展望。整体汇报会控制在本科毕业设计的实现范围内，不把系统夸大成企业级云盘。

## 3. 研究背景与意义

这一页我想说明的是选题为什么有意义。平时课程设计、项目资料和文档越来越多，本地文件夹可以存，但在共享、预览和归档上不够方便。另一个问题是部署：毕业设计系统换到答辩环境时，数据库、缓存、静态资源路径和文件目录权限都可能出问题。所以我把课题定位为一个轻量级云文件管理系统，并且用容器化方式让它更容易复现。讲这一页时可以指左侧的访问关系图，说明系统不是单个页面，而是浏览器、代理、后端和数据层共同组成的运行链路。

## 4. 研究目标与技术路线

这一页把目标和路线合在一起讲。左侧是系统完成的功能范围，包括登录认证、文件上传、目录管理、下载预览、分享访问、回收站、存储统计和容器部署。右侧是实现路线：先做需求分析和总体设计，再实现核心功能，最后用 Docker Compose 部署并测试。这里我会特别说明边界：本系统不是企业级多租户平台，也不引入复杂审批流或大规模分布式存储，重点是完成本科毕设范围内可运行、可演示、可验证的系统。

## 5. 系统总体设计

接下来进入系统设计。这一页重点看右侧总体架构图：浏览器先访问 Nginx，Nginx 返回前端页面，同时把接口请求转发给 Spring Boot 后端。后端负责用户认证、文件管理、分享、回收站、统计和预览控制。MySQL 保存用户、文件、分享和回收站等元数据，Redis 保存上传分片或转码进度等临时状态，本地目录保存真实上传文件。讲的时候可以顺着底部“浏览器 → Nginx → Spring Boot → MySQL / Redis / 文件目录”这条链路走一遍。

## 6. 容器化部署流程

这一页讲部署流程。执行 docker compose up -d --build 后，Compose 会先构建后端镜像，创建内部网络和数据卷，再启动 MySQL 与 Redis。MySQL 健康检查通过后，后端服务启动，并执行兼容补丁，例如补齐 user_id 字段、索引和 demo 演示账号。最后 Nginx 作为统一入口提供访问。讲截图时可以指底部终端区域，说明这里展示的是实际容器启动状态，不是画出来的示意图。

## 7. 容器编排关系与功能支撑

这一页重点讲容器之间怎么配合。lfs-nginx 对外暴露 80 端口，负责静态资源和反向代理；lfs-backend 运行 Spring Boot 业务接口；lfs-mysql 保存业务数据；lfs-redis 保存短生命周期状态；volume 负责文件和数据持久化。这里要强调的是，上传、下载、预览、分享、回收站和统计都不是某一个页面单独完成的，而是由这些容器和数据关系共同支撑。

## 8. 核心功能实现一：文件管理

这一页讲文件管理。上传文件时，系统一边把物理文件保存到持久化目录，一边把文件名、大小、类型、父目录和归属用户写入 lfs_file 表。目录本身也作为记录保存，通过 is_dir 区分。移动文件主要更新 parent_id，删除操作进入回收站，而不是立即清理物理文件。讲右侧截图时，可以指文件列表中的文件类型和时间列，说明这是系统真实保存和读取元数据后的展示效果。

## 9. 核心功能实现二：预览与分享

这一页讲预览和分享。预览模块的关键不是简单打开文件，而是把 /api/files、/api/thum 和 /api/trans 这几类路径统一收敛到 FilePreviewController。后端会做路径归一化、secret 和 expire 的签名校验、路径越界检查，再根据文件类型返回响应。右侧截图里可以指“分享创建”和“分享访问”两块，说明系统已经完成从生成分享链接到匿名访问分享内容的闭环。

## 10. 核心功能实现三：用户隔离、回收站与统计

这一页讲用户视角。系统保留 admin 和 demo 两类账号：admin 可以看全量数据，demo 只能看自己的文件空间。这个隔离不是前端隐藏按钮，而是后端通过 CurrentUserService 识别当前用户，再在文件列表、回收站和统计查询中追加 user_id 条件。讲截图时可以指 demo 用户文件空间，说明页面看到的内容和统计结果都跟当前用户绑定，避免列表不可见但统计仍计入的问题。

## 11. 系统测试与验证

这一页讲测试。顶部三个数字分别表示 17 个功能与异常测试项、5 个自动化测试类和 24 个自动化用例通过。表格里把 17 项拆成四类：容器层 4 项、业务层 5 项、访问控制 4 项、异常回归 4 项，这样 17 的来源是清楚的。这里我会说明，测试重点是验证关键链路稳定，比如容器启动、登录、上传、预览、分享、回收站、双用户隔离和非法访问拒绝；不把它包装成论文中没有给出数据的性能评测。

## 12. 系统运行界面一：登录与文件空间

接下来三页是运行界面展示。这一页先看基础入口：左上是登录页面，右上是文件列表，左下是普通用户文件空间。讲的时候可以指文件列表里的目录结构、文件类型和时间信息，说明登录后页面不是静态截图，而是后端返回文件元数据后渲染出来的文件空间。

## 13. 系统运行界面二：预览与分享

这一页看预览与分享效果。左上是文件预览界面，右侧是分享创建和分享访问页面。这里可以指分享弹窗里的链接和有效期字段，再指匿名访问页，说明分享不是只弹出一个窗口，而是后端保存分享码和有效期后，形成了创建、校验、访问的完整链路。左下调试截图可以辅助说明预览链路在浏览器中实际返回成功。

## 14. 系统运行界面三：统计与容器状态

这一页展示的是运行状态。左侧是用户视角与文件列表相关页面，用来说明文件、回收站和统计使用同一套用户过滤逻辑。右侧终端截图可以重点指容器状态区域，说明 Nginx、后端、MySQL、Redis 是按 Compose 编排一起启动的。这里的作用是证明系统不是只完成页面，而是部署后能完整运行。

## 15. 总结与展望

最后总结一下，本课题的三个主要亮点是：第一，容器化一键部署，用 Docker Compose 编排 Nginx、后端、MySQL 和 Redis，降低环境差异；第二，预览链路统一治理，通过 FilePreviewController 收敛路径归一化、签名校验和越界检查；第三，双用户视角隔离，通过 CurrentUserService 和 user_id 过滤支撑 admin 与 demo 两类访问视角。不足方面，权限模型还比较轻量，存储仍以本地目录为主，监控和运维能力也比较基础。后续可以继续扩展团队空间、对象存储、分享策略、日志监控和预览缓存。我的汇报到此结束，感谢各位老师，敬请批评指正。
