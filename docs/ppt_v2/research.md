## 答辩讲稿（每页 30-45 秒口播）

### P1 封面（10 秒）

各位老师好，我是网络工程 2203 班的杨佳星，学号 04222088。我的毕业论文题目是《基于容器化部署的云文件管理系统设计与实现》，指导教师是王晓梅老师。下面开始汇报。

### P2 目录（10 秒）

本次汇报分为四个部分：选题背景与研究目标、系统设计与容器化部署、核心功能实现，以及测试验证与运行展示。

### P3 研究背景与意义（45 秒）

本课题来源于本科毕设的真实痛点。文件管理系统功能本身并不难，但传统部署方式下，依赖版本、数据库初始化脚本、静态资源路径、文件目录权限等都和运行环境高度耦合。一旦换台机器或者数据卷被清掉，重新启动经常要花很长时间。所以本课题关注的核心矛盾，不是"能不能做出来"，而是系统能否稳定地部署、运行、演示、验证。容器化方案正好解决环境一致性问题——一键启动、版本钉死、数据持久化、跨机复现。

### P4 研究目标与技术路线（40 秒）

研究目标分两条主线，共 8 项功能：登录、上传、目录、预览、分享、回收、统计、以及容器化部署。技术路线方面，前端用 Vue 3 + Element Plus + Vite，后端用 Spring Boot 3.2.2 + MyBatis-Plus，安全用 JWT + BCrypt，数据层 MySQL 8 + Redis 7，部署层 Nginx + Docker + Docker Compose，文件处理用 Aspose + PDFBox + JAVE。需要说明的是边界：本课题不构建多租户体系，也不引入完整 RBAC，更不做配额管理。

### P5 系统总体架构（40 秒）

系统采用前后端分离的 B/S 架构。浏览器请求先到 Nginx，Nginx 一方面返回前端静态页面，另一方面把 /api 请求反向代理给后端 Spring Boot。后端负责认证、文件管理、分享、回收站、统计和预览访问控制。MySQL 保存业务元数据，Redis 保存短生命周期临时状态，本地持久化目录保存真实上传文件。整体分五层：表现层、业务层、数据层、部署层、文件处理层，职责清晰、便于排查。

### P6 容器化部署流程（45 秒）

容器化部署是本课题的重点之一。从命令到就绪共 7 步：执行 docker compose up -d --build 后，先构建后端镜像并把所有版本钉死；然后创建内部网络和数据卷；接着启动 MySQL 和 Redis 两个基础容器；MySQL 健康检查通过后，再启动后端服务，并执行数据库兼容补丁，比如自动补齐 user_id 字段、索引和 demo 演示账号；最后启动 Nginx 作为统一入口。整个过程一条命令完成，答辩现场任何一台机器都能稳定复现。

### P7 容器编排关系（45 秒）

容器编排关系是另一个重点。系统由 4 个容器协同：lfs-nginx 对外暴露 80 端口负责静态资源和反向代理，lfs-backend 跑 Spring Boot 业务接口，lfs-mysql 保存业务数据，lfs-redis 保存上传分片状态和转码进度等临时信息。它们之间的网络关系是：浏览器到 nginx，nginx 反代到 backend，backend 同时连接 mysql 和 redis。数据卷把上传目录、MySQL 数据、Nginx 配置都映射回宿主机，容器即使被销毁重建数据也不会丢。所有功能——上传、预览、分享、回收、统计——都依赖这套编排协同支撑。

### P8 核心功能①：文件上传与管理（40 秒）

文件管理模块的核心是双写一致：上传时，物理文件落到持久化目录 /files，元数据同步写入 lfs_file 表，包含文件名、大小、类型、parent_id、user_id、is_dir 等字段。秒传机制基于 MD5 比对，相同内容只占一份物理空间，演示场景下显著节省。删除是软删除，文件进入回收站标记字段，不立即物理删除，方便恢复。

### P9 核心功能②：预览访问链路修复（55 秒，亮点页）

这一页是本课题最重要的工程亮点。系统中有三类预览路径——/api/files、/api/thum、/api/trans，原本各自处理时，在 Nginx 反向代理叠加签名校验的环境下，频繁出现路径错乱、签名失效，预览经常返回 failed。我把这三类路径统一交给 FilePreviewController 处理，做了三件事：第一，路径归一化；第二，secret + expire 签名校验，服务端密钥 + 过期时间戳，攻击者既无法离线构造签名，也无法在不破坏签名的前提下延长 URL 有效期；第三，路径越界检查，归一化后必须落在 /files 根目录内，杜绝 ../ 攻击。改造后预览链路稳定，分享访问、缩略图、转码资源全部共用这套校验。

### P10 核心功能③：双用户隔离（35 秒）

为了演示需要，系统设计了两类账号：admin 是管理员视角，可以查看全量数据；demo 是普通演示用户，只能看到自己的文件空间。这个隔离不是靠前端隐藏按钮做的，而是后端通过 CurrentUserService 识别当前用户，再在文件列表、回收站、统计这些查询里强制追加 user_id 条件。lfs_file 表里的 user_id 字段就是为了这个隔离机制服务的。

### P11 系统测试（35 秒）

测试覆盖四个层面：容器层、业务层、访问控制层、异常回归层。功能测试整理了 17 项，从容器启动、数据库兼容补丁，到登录、上传、预览、分享、回收、双用户隔离、非法访问拒绝。自动化测试有 5 个测试类共 24 个用例，覆盖当前用户识别、兼容补丁、分享服务、存储统计、预览控制器，全部通过。测试目标是验证关键链路稳定，没有包装没有数据支撑的性能评测。

### P12 运行界面①：登录与文件空间（25 秒）

这是第一组真实运行界面。左边是登录入口，输入账号密码后进入文件管理主界面，可以看到目录结构、文件列表、文件类型、修改时间等。这是系统作为 Web 应用的基础状态。

### P13 运行界面②：上传 / 预览 / 分享（25 秒）

这是第二组运行界面。左边是分享创建弹窗，可以生成分享码并设置有效期；右边是文件预览成功的效果。预览链路在反向代理下稳定返回，分享访问是匿名的，对应前面讲的预览链路修复和分享码机制。

### P14 运行界面③：容器运行状态（25 秒）

这是第三组运行界面。左边是 docker ps 命令的输出，可以看到 4 个容器全部 Up 状态；右边是终端跑自动化测试，24 个用例全部 PASS。这两张图说明系统从部署到业务的完整闭环都能稳定运行。

总结一下。本课题完成了云文件管理系统的总体架构设计，实现了完整业务闭环、容器化一键部署、预览链路修复和轻量双用户隔离。不足之处也比较清楚：权限模型简单，没引入完整 RBAC；存储以本地目录为主，没接对象存储；监控运维基础。后续可以继续扩展团队空间、对象存储、分享策略升级和日志监控。
