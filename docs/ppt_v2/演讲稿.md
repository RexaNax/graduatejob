## 第 3 页｜研究背景与意义（约 35 秒）

先说背景。

平时我们做 Web 项目的时候，部署其实是个挺头疼的事。换一台机器跑，经常就遇到这四类问题：（看左边图）环境耦合、依赖版本对不上、初始化脚本要手动跑、目录权限还要自己配。一套流程走完，半天就过去了。

容器化的思路就是把这些问题一次性收敛掉：（看右边图）一键启动、版本钉死、数据持久化、跨机一致复现。

所以这个课题我关注的不是"功能能不能做出来"，而是这个系统能不能稳定地部署、运行、演示和验证。这是我整个工作的出发点。

## 第 4 页｜研究目标与技术路线（约 40 秒）

基于刚才的目标，我设计了上面这八个功能模块：登录认证、文件上传、目录管理、在线预览、分享访问、回收站、存储统计，再加上容器化部署。

下面这条横向的技术路线，是我整个项目的技术选型：

前端用 Vue3 加 Element Plus，配 Vite 做构建；
后端用 Spring Boot 3.2.2 加 MyBatis-Plus；
安全这块用 JWT 加 BCrypt 做无状态鉴权和密码加盐；
数据层是 MySQL 8 存元数据、Redis 7 存临时状态；
部署用 Nginx 做反向代理，外面用 Docker Compose 编排；
文件处理用了 Aspose、PDFBox 和 JAVE 三个库，覆盖文档、PDF 和音视频格式。

底下这一行是边界说明：本系统不做多租户、不做完整的 RBAC、也不做配额管理，只做轻量的用户隔离。

## 第 5 页｜系统总体架构（约 45 秒）

这一页是系统的总体架构图。

整体我分成五层：

最上面是表现层，就是 Vue 3 写的单页前端；
往下是业务层，所有业务逻辑都在 Spring Boot 的 REST 接口里；
再往下是数据层，MySQL 存文件元数据和用户信息，Redis 存临时状态，比如分享码的有效期；
左边的部署层是 Nginx，它一方面提供静态资源，一方面把 `/api` 的请求反向代理到后端；
最下面单独抽出来一个文件处理层，用 Aspose 处理 Office 文档、PDFBox 处理 PDF、JAVE 处理音视频，把多格式预览这一块封装在一起。

这样分层之后，前后端是完全解耦的，部署和扩展都比较灵活。

## 第 6 页｜容器化部署（约 50 秒）

这一页是我整个工作里比较核心的一部分——容器化部署。

左边这张图是 Compose 编排出来的四个容器：用户请求先打到 Nginx，由 Nginx 把静态资源直接返回，把 API 请求转发给 Backend，Backend 再去访问 MySQL 和 Redis。四个容器跑在同一个自定义网络里，对外只暴露 Nginx 一个入口。

右边这条流程是 `docker compose up -d --build` 之后实际发生的事：

第一步下发启动命令；
第二步拉取或者构建镜像；
第三步创建网络和数据卷；
第四步先把 MySQL 和 Redis 起起来；
第五步等健康检查通过；
第六步再启动后端，并且执行兼容性补丁脚本；
最后第七步 Nginx 入口就绪，整个系统就可以对外提供服务了。

也就是说，无论换到哪台机器，只要装了 Docker，一行命令就能把整套系统跑起来，环境完全一致。

## 第 7 页｜核心实现①：文件上传与管理（约 50 秒）

下面挑两个核心功能展开讲一下。

第一个是文件上传与管理。上面这张流程图是上传的完整链路。

我设计的时候有三个比较关键的点：

第一个是物理文件和元数据双写。文件本身落到 `/files` 目录下，文件名、大小、MD5、所属目录这些元数据写到 `lfs_file` 表里，两边通过 MD5 关联。

第二个是 MD5 秒传。前端在上传之前先算文件的 MD5，发到后端做查询，如果数据库里已经存在相同 MD5 的物理文件，就不再重复上传，直接给当前用户挂一条元数据记录。这样同一份内容在磁盘上只占一份空间，上传也几乎瞬时完成。

第三个是软删除。删除文件并不会立即把物理文件清掉，而是在元数据上打一个回收站标记，超过保留期之后再异步清理。这样用户误删之后还能找回来。

## 第 8 页｜核心实现②：JWT 鉴权与用户隔离（约 55 秒）

第二个核心功能是鉴权和用户隔离。

我用的是 JWT 这种无状态的方案，整个流程分成五步：

第一步，用户登录成功之后，后端用 HMAC 算法签一个 token 返回给前端；
第二步，前端把 token 放在请求头里带回来，整个过程不依赖 cookie 或者 session；
第三步，后端在拦截器里验签和检查过期时间，非法或者过期就直接返回 401；
第四步，校验通过之后把 userId 注入到当前请求的上下文里；
第五步也是最关键的一步，所有数据库查询的 SQL，都强制带上 `WHERE user_id = ?` 这个条件，从数据层把不同用户的数据隔开。

这样做有三个好处：服务端无状态，水平扩展容易；HMAC 签名保证 token 没法被伪造；最重要的是隔离是在后端强制执行的，前端怎么改都绕不过去。

底下这一行是现场演示的两个账号：admin 是管理员视角，demo 是普通用户视角，他们登录之后看到的文件空间是完全互不可见的。

## 第 12 页｜总结与展望（约 50 秒）

最后做一个简短的总结。

左边是这次已经完成的工作，主要是四点：

第一，做出了一个完整的业务闭环，包含登录、上传、目录、预览、分享、回收和统计；
第二，实现了容器化的一键部署，四个容器通过 Compose 编排，跨机器可以一致复现；
第三，专门修复了预览链路的几个问题，加了 secret 和 expire 签名校验，并对路径做了归一化；
第四，做了轻量级的双用户隔离，从 SQL 层强制带 user_id 条件。

右边是我自己分析下来的一些不足和后续可以扩展的方向：

第一，权限模型还比较简单，没有引入完整的 RBAC；
第二，存储目前是本地目录，后面可以接入对象存储，比如 OSS 或者 MinIO；
第三，监控和运维比较基础，还缺少日志聚合和指标采集这些能力。

这些是我后面如果继续做下去，会优先去补的方向。
