## 第 3 页 · 研究背景与意义

> （切到左右对照图）

本课题面向的是一个非常具体的工程痛点：**文件管理类系统部署难**。

传统部署存在四个典型问题——**环境耦合、依赖版本不一致、初始化脚本繁琐、目录权限容易出错**，导致项目"在我电脑上能跑、换台机器就崩"。

容器化方案恰好对应这四点提供了答案——**一键启动、版本钉死、数据持久化、跨机一致复现**。

所以这一页我想强调的结论是：**本课题关注的不是"能不能做出来"，而是"系统能否稳定部署、运行、演示和验证"。**

## 第 4 页 · 研究目标与技术路线

> （上半区指着 8 个目标方块）

我把研究目标拆成 **8 个具体功能**：登录认证、文件上传、目录管理、在线预览、分享访问、回收站、存储统计、容器化部署。

> （下半区横向时间轴）

技术路线整体是一条标准的全栈链路：前端 Vue3 加 Element Plus，后端 Spring Boot 3.2.2 加 MyBatis-Plus，安全用 JWT 加 BCrypt，数据层 MySQL 8 加 Redis 7，部署用 Nginx 加 Docker Compose，文件处理引入 Aspose、PDFBox 和 JAVE 三个库。

> （指底部边界声明）

需要说明的边界是：本系统**不做多租户、不做完整 RBAC、不做配额管理**，聚焦在"单组织内的文件管理 + 容器化交付"这条主线上。

## 第 5 页 · 系统总体架构

> （指左侧大图）

这是系统的总体架构图，整体分成五层：

- **表现层** 是 Vue 3 单页应用；
- **业务层** 是 Spring Boot 提供 REST 接口；
- **数据层** 由 MySQL 存元数据、Redis 存临时状态（比如登录 token、分享码）；
- **部署层** 由 Nginx 既托管前端静态资源、又做后端反向代理；
- **文件处理层** 是为预览能力单独抽出来的，集成了 Aspose、PDFBox、JAVE 三个组件。

这五层后续都通过 Docker Compose 统一编排起来。

## 第 6 页 · 容器化部署流程

> （切到 7 步流程图，这是要重点讲的页）

这一页讲的是**部署一条命令背后到底发生了什么**。

输入只有一行：`docker compose up -d --build`。

之后系统按 7 步自动完成：① 拉取并构建镜像（版本是钉死的）；② 创建网络和数据卷；③ 启动 MySQL 和 Redis；④ 等 MySQL 健康检查通过；⑤ 启动后端，并在启动时自动跑兼容补丁——给老库补 `user_id` 字段、补缺失的索引、初始化 demo 演示账号；⑥ 最后启动 Nginx 作为统一入口。

结论一句话：**一条命令完成全栈拉起，答辩现场任何一台机器都能复现**。

---

## 第 7 页 · 容器编排关系

> （指上排 4 个容器卡片）

实际跑起来一共是 4 个容器：

- `lfs-nginx`：用 Alpine 版 Nginx，对外暴露 80 端口，镜像约 50M；
- `lfs-backend`：基于 OpenJDK 17，跑 Spring Boot，内部 8080 端口；
- `lfs-mysql`：MySQL 8，3306 端口；
- `lfs-redis`：Alpine 版 Redis 7，6379 端口。

> （指下方箭头）

调用关系是：**浏览器 → Nginx → 后端 → MySQL / Redis**。Nginx 是唯一对外端口，后端、数据库都不直接暴露，安全性更好。

> （指最下方四个数据卷）

四个数据卷分别挂载文件目录、MySQL 数据、Redis 数据和 Nginx 配置，**容器销毁数据不丢**。

## 第 8 页 · 核心实现① · 文件上传与管理

> （指上方上传时序图）

文件上传流程的关键是**三件事**：

第一，**物理文件 + 元数据双写**：物理文件落到 `/files` 目录，元数据写到 `lfs_file` 表，两者通过 MD5 关联。

第二，**MD5 秒传机制**：上传前先算 MD5，如果库里已有相同 MD5，就只新增一条元数据记录，物理文件不重复落盘——**相同内容只占一份空间**。

第三，**软删除入回收站**：删除并不直接删物理文件，而是把元数据置为"已删除"状态进回收站，可以恢复，也能彻底清空。

## 第 9 页 · 核心实现② · 预览访问链路修复（★ 工程亮点）

> （这是工程亮点页，可以稍微放慢，多停 1–2 秒）

这一页是我整个项目里**改造工作量最大、也最能体现工程价值**的部分。

最初我的预览功能在 Nginx 反代下频繁返回 `failed`，原因是预览资源的路径和签名校验逻辑分散在三个 Controller 里、行为不一致。

我做的改造概括成三点：

1. **三类路径统一**：原始文件 `/api/files`、缩略图 `/api/thum`、转码资源 `/api/trans` 全部归到 `FilePreviewController` 里走同一套校验入口。

2. **secret + expire 签名**：每个预览 URL 都带一个签名和过期时间，**既防盗链、又能给即将过期的链接续命**，避免用户预览到一半失效。

3. **路径越界检查**：所有路径在使用前会做归一化，**必须落在 `/files` 这个根目录里**才能放行，杜绝 `../` 类型的路径穿越。

改造完成后，预览、分享、缩略图、转码 4 个入口共用同一套安全校验，**链路稳定下来**。

## 第 10 页 · 核心实现③ · 双用户隔离

> （左右两个卡片对照）

系统内置了两个演示账号：左边的 `admin` 是管理员视角，看到的是全量数据，用来演示后台运维；右边的 `demo` 是普通用户视角，**只能看到自己的文件空间**，用来演示终端用户使用。

> （指底部说明）

需要强调的是，**用户隔离不是靠前端隐藏，而是后端硬隔离**：每个文件记录都带 `user_id` 字段，后端通过 `CurrentUserService` 取当前登录用户，**在所有相关 SQL 上强制追加 `user_id` 条件**，保证数据从数据库这一层就被隔开。

## 附录 A · 评委可能追问 & 参考答法

| # | 可能问题 | 参考回答要点 |
|---|---------|------------|
| 1 | 为什么用 Docker Compose 而不是 Kubernetes？ | 课题定位是"单机一键拉起 + 答辩可复现"，Compose 足够；K8s 适合多节点生产场景，超出本课题边界。 |
| 2 | MD5 秒传如果碰撞了怎么办？ | MD5 碰撞概率极低，且业务场景是个人文件管理，不是安全敏感场景；必要时可叠加 SHA-256 二次校验。 |
| 3 | secret + expire 签名怎么算的？防止伪造吗？ | 服务端用密钥对（文件路径 + 过期时间戳）做 HMAC，URL 里带 secret 和 expire；服务端用同一密钥重算比对，密钥不出后端，无法伪造。 |
| 4 | user_id 隔离如果忘了加条件怎么办？ | 通过 `CurrentUserService` 统一注入，所有涉及用户文件的 Service 方法**强制要求传入 user_id**，并在 SQL 层 where 条件里追加；测试类 `CurrentUserServiceTest` 专门覆盖这一点。 |
| 5 | 如果 MySQL 容器挂了，数据会丢吗？ | 不会。MySQL 数据通过 `./mysql-data` 卷持久化在宿主机，容器重建后挂回原卷即可恢复。 |
| 6 | 预览为什么要归一化路径？ | 防止 `../` 路径穿越攻击访问到 `/files` 之外的系统文件；归一化后用前缀比对，只放行落在 `/files` 内的请求。 |
| 7 | 为什么前端用 Vue 3 而不是 React？ | 个人技术栈选型，Vue 3 + Element Plus 上手快、生态完整，与本课题工作量匹配。 |
| 8 | Aspose 是商业组件，正式上线怎么办？ | 答辩演示用社区/试用版即可；正式环境可替换为 LibreOffice headless 转换或购买 Aspose 商业授权。 |
| 9 | Schema 兼容补丁是干什么的？ | 用来兼容旧库：自动给老 `lfs_file` 表加 `user_id` 字段、补必要索引、初始化 demo 账号，让老数据库也能直接跑新代码。 |
| 10 | 24 个用例覆盖率多高？ | 用例聚焦在**关键链路**（用户上下文、Schema 兼容、分享、统计、预览），不是行覆盖率指标，而是**业务场景覆盖**，关键路径全覆盖。 |
