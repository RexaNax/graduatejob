## 第 3 页 · 研究背景与意义（40 秒）

> 这页对比的是传统部署和容器化部署的差异。  
> **传统部署**面临 4 个痛点：环境耦合（不同机器 Java/MySQL 版本不一样）、依赖版本漂移、初始化脚本要手动跑、目录权限要手动配。这些问题在答辩或交付场景里非常致命——**不是写不出来，而是换台机器跑不起来**。  
> **容器化方案**用一条命令解决：版本钉死在镜像里、数据通过 volume 持久化、跨机一致复现。  
> 所以**我这个课题的关注点不是"能不能做"，而是"系统能否在评审组任何一台机器上稳定运行、演示、验证"**。这也是为什么我选择把容器化部署作为整个课题的核心抓手。

## 第 5 页 · 系统总体架构（45 秒）

> 系统是经典的 5 层架构：  
> **表现层** 是 Vue 3 单页应用；**业务层** 是 Spring Boot 提供 REST 接口；**数据层** 用 MySQL 存元数据、Redis 存登录态等临时状态；**部署层** 用 Nginx 作为统一入口、做反向代理和静态资源托管；**文件处理层** 集成 Aspose、PDFBox、JAVE，支持 Office、PDF、视频等多格式预览。  
> 这一页只是把全貌摆出来，下一页我重点讲容器化是怎么把这 5 层装进 4 个容器里、并用一条命令拉起来的。

## 第 6 页 · 容器化部署：Compose 编排 + 启动流程（70 秒，**重点页**）

> 这是我的工程亮点之一。左边是我的 **docker-compose.yml** 真实片段（文件就在 `project/deploy/` 目录），定义了 4 个 service：nginx、backend、mysql、redis。右边是这条 `docker compose up -d --build` 命令背后的 **7 步启动流程**。  
>  
> 我重点讲三个点：  
> **第一**，依赖管理。compose 里 backend 显式声明了 `depends_on: mysql.service_healthy + redis.service_started`——也就是说后端必须等 MySQL 健康检查通过、Redis 启起来之后才会启，避免传统部署里"后端连不上数据库"这种典型问题。  
> **第二**，第 6 步"后端启动 + 兼容补丁"是我自己加的工程化处理。系统第一次启动时，后端会自动给数据库补 `user_id` 字段、补索引、初始化 demo 账号——这样换一台机器拉起，**不需要任何人工 SQL 操作**。  
> **第三**，所有版本钉死、数据卷映射到宿主机。哪怕容器被删，业务数据也不会丢。  
>  
> 老师如果问"为什么不用 Kubernetes"——本课题是单机部署，4 个容器规模，K8s 是杀鸡用牛刀；Compose 在这个量级是最合适的方案。

## 第 7 页 · 核心实现①：文件上传与管理（50 秒）

> 这是文件上传链路图。我重点讲 3 个工程亮点：  
> **第一，物理文件 + 元数据双写**。前端切片上传到后端，后端把物理文件落到 `/files` 目录，元数据写到 `lfs_file` 表——两边解耦，物理存储和数据库可以独立优化。  
> **第二，MD5 秒传**。文件上传前先算 MD5 哈希，如果哈希在数据库里已经存在，**直接复用物理文件，秒级返回**。比如同一个 PDF 在系统里被多个用户上传，磁盘上只占一份空间。  
> **第三，软删除入回收站**。删除操作只是改一下 `is_deleted` 字段，物理文件不动；用户可以从回收站恢复，30 天后再做物理清理——避免误删。

---

## 第 8 页 · 核心实现②：JWT 鉴权与用户隔离（70 秒，**工程亮点**）

> 这是另一个工程亮点。整个鉴权流程是 5 步：  
> **登录签发** → 用户登录成功后，后端 `JwtConfig.genUserToken` 用用户 id 和用户名生成 token，签上 HMAC 签名；  
> **请求携带** → 前端把 token 放在每个请求的 `token` 请求头里，服务端无 cookie 无 session；  
> **校验解析** → 后端拦截器调用 `parseToken` 验签 + 检查过期，非法直接 401；  
> **注入上下文** → 校验通过后 `CurrentUserService` 把 userId 放进当前请求上下文；  
> **数据隔离** → 所有业务 SQL **强制追加 WHERE user_id = ?** 条件。  
>  
> 三大亮点：**无状态**所以易水平扩展；**HMAC 签名**让任何篡改都会被拒绝；**后端强制隔离**——前端隐藏不被信任，**任何越权请求都会在 SQL 层被拦下**。  
>  
> 现场演示我准备了两个账号：**admin** 是管理员视角，**demo** 是普通用户视角。两个账号登录后拿到各自不同的 token，看到的文件空间互相不可见——这就是 JWT + user_id 双层防御的实际效果。  
>  
> 老师如果问"JWT 怎么防伪造"——服务端 appSecret 是私有的，攻击者构造 token 没法签出正确的 HMAC，verify 阶段会直接抛异常，请求被拒。token 本身有 4 小时过期，过期之后必须重新登录。

## 答辩预演 · 高频问答准备

| 老师可能问 | 你怎么答（核心抓手） |
|---|---|
| 为什么用 Docker Compose 不用 Kubernetes？ | 单机 4 容器规模 K8s 太重，Compose 在这个量级是最合适的；如果未来扩展到多机，可以无缝迁移到 K8s（service 定义大体可复用）。 |
| JWT 怎么保证安全？ | HMAC 签名 + 服务端 appSecret 私有 + 4 小时过期；任何篡改 token 在 verify 阶段被 com.auth0.jwt 直接拒绝。 |
| 怎么防止用户看到别人的文件？ | 双层防御：① 后端拦截器解析 token 注入 userId；② 业务 SQL 强制追加 `WHERE user_id = ?`；前端隐藏不被信任。 |
| 文件上传秒传是怎么做的？ | 前端先算 MD5 → 后端查 `lfs_file` 表是否已有相同 hash → 命中则复用物理文件，只插一条新元数据。 |
| 如果一个文件正在预览时被删除会怎样？ | 软删除只改 `is_deleted` 标记，物理文件不动；预览链路通过 secret+expire 签名验证，不依赖文件状态，所以正在播的视频不会被中断。 |
| 测试覆盖率怎么样？为什么不是 100%？ | 24 个自动化用例覆盖核心后端服务（用户上下文、Schema 兼容、分享、存储统计、预览控制器）；前端因课题侧重后端工程化没引入 e2e。 |
| 你这个课题独立完成了哪些？ | ① 容器化部署方案落地；② 预览链路 3 类路径统一签名；③ JWT + user_id 双层隔离；④ 自动化测试 24 例；⑤ 启动时数据库兼容补丁脚本。这些都是我自己写的。 |
| 不足之处你最想优先补的是哪个？ | RBAC 权限模型——目前 admin/demo 是硬编码角色，扩展到团队场景必须有规范的角色-权限表设计。 |
