# 多用户隔离设计说明

## 目标

在现有凌夕文件管理系统基础上，补齐适合毕业设计演示的轻量多用户隔离能力。

本次设计只覆盖以下目标：

1. 系统预置两个账号：`admin` 和 `demo`
2. `admin` 作为管理员，可以查看全部文件数据
3. `demo` 作为普通用户，只能查看和操作自己的文件空间
4. 分享链接继续支持匿名访问，便于演示“登录管理 + 外链分享”两种能力
5. 不引入复杂的租户、组织、角色矩阵、自助注册或协同编辑

## 现状结论

当前代码已经具备用户表、用户登录和用户 JWT：

1. `sys_user` 已存在，且已有 `admin` 账号初始化逻辑
2. `/user/login` 已返回用户 token
3. JWT 中已经保存 `userId` 和 `username`

但系统仍然不是多用户系统，原因有两点：

1. `UserService` 和 `GlobalInterceptor` 仍限制只有 `admin` 可登录业务系统
2. `lfs_file` 表没有归属用户字段，导致所有文件仍处于同一个公共空间

因此，本次工作的本质不是“新加登录”，而是“补齐文件归属与权限过滤”。

## 设计方案

采用“管理员全局可见 + 普通用户私有空间”的轻量模型。

### 用户模型

系统预置两个账号：

1. `admin`
2. `demo`

权限规则：

1. `admin` 可以查看全部文件、全部回收站记录、全部分享记录、全局统计
2. `demo` 只能查看和操作自己创建的文件、文件夹、回收站记录、分享记录

本次不开放自助注册，不做用户管理后台，不做密码找回，不做用户间消息通知。

### 数据模型

在 `lfs_file` 表新增字段：

1. `user_id BIGINT(20) NOT NULL DEFAULT 1`

语义：

1. 文件或文件夹的归属用户 ID
2. 新上传文件、新建文件夹都写入当前登录用户的 `user_id`
3. 历史数据统一归属为 `admin`

本次不额外给 `lfs_file_share`、`lfs_file_trash` 增加 `user_id` 字段。

原因：

1. `lfs_file_share` 已经通过 `file_id` 关联文件，文件归属可以反查
2. `lfs_file_trash` 也可以通过 `file_id` 找到原始文件归属
3. 对毕业设计来说，这样已经足够，能显著减少迁移和改动面

### 权限判定

后端统一通过 token 获取当前用户：

1. 从请求头 `token` 中解析 `userId`
2. 查询 `sys_user`
3. 判断是否为管理员

统一规则：

1. 管理员：不过滤 `user_id`
2. 普通用户：所有文件相关查询和写操作都要求 `user_id = 当前用户`

建议增加一个轻量用户上下文工具，集中提供：

1. `getCurrentUserId()`
2. `getCurrentUsername()`
3. `isAdmin()`

这样可以避免在各个 Service 中重复写 token 解析逻辑。

## 受影响功能

### 1. 登录

变更：

1. 取消“只有 `admin` 能登录”的限制
2. 允许所有状态正常用户登录
3. 登录成功后前端继续复用现有 token 存储逻辑

返回给前端的用户信息里，建议显式展示：

1. `id`
2. `username`
3. `nickname`
4. 是否管理员

这样前端可以在页面顶部展示“当前用户：管理员 / 普通用户”。

### 2. 文件列表与目录树

普通用户查询文件列表时：

1. 只返回自己的根目录文件
2. 搜索时也只在自己的文件范围内搜索
3. 目录树也只展示自己的文件夹

管理员查询文件列表时：

1. 继续保留全局可见

### 3. 文件详情、上传、删除、移动、重命名

所有基于文件 ID 的操作都必须增加“当前用户是否有权访问该文件”的校验。

普通用户：

1. 只能查看自己的文件详情
2. 只能删除自己的文件
3. 只能移动自己的文件到自己的目录
4. 只能重命名自己的文件
5. 上传完成后生成的文件记录必须绑定自己的 `user_id`

管理员：

1. 保持全量访问能力

### 4. 回收站

普通用户只能看到自己删掉的文件所对应的回收站记录。

管理员可以看到全部回收站记录。

删除、恢复、清空回收站时，也必须做同样的权限边界校验。

### 5. 分享

分享创建和取消时：

1. 普通用户只能对自己的文件创建分享和取消分享
2. 管理员可对任意文件创建分享和取消分享

匿名访问分享链接时：

1. 不校验当前登录用户
2. 仍按 `shareCode` 正常访问

这样分享能力不会因为多用户隔离而退化。

### 6. 统计

存储统计建议采用双模式：

1. 管理员查看全局统计
2. 普通用户查看自己的已用空间和文件数量

这会让系统更像完整产品，也很适合答辩时展示“不同身份看到的数据不同”。

## 前端表现

前端不需要大改，建议只做最小增强：

1. 顶部导航显示当前用户名和角色
2. 登录后把 `user` 一并缓存，或通过 `/user/info` 获取当前用户信息
3. 文件页、回收站、分享页继续复用现有接口，不单独做复杂权限 UI

说明：

权限边界主要放在后端做，前端只负责展示当前身份和承接接口返回结果。

## 数据初始化

需要更新初始化 SQL：

1. 给 `lfs_file` 增加 `user_id`
2. 给历史数据补默认值，归属 `admin`
3. 新增 `demo` 用户初始化记录

建议账号如下：

1. `admin / 123456`
2. `demo / 123456`

这样便于演示，文档和答辩说明也简单清楚。

## 测试与验收

至少覆盖以下验收场景：

1. `admin` 登录后能看到现有全部文件
2. `demo` 登录后只能看到自己的文件
3. `demo` 上传文件后，`admin` 能看见，`demo` 能看见，其他普通用户看不见
4. `demo` 无法访问或删除 `admin` 的文件详情
5. `demo` 创建的分享链接可匿名访问
6. `admin` 和 `demo` 的回收站内容不同
7. 预览修复仍然有效，不因多用户改动回归

## 本次不做的内容

为控制毕业设计工作量，本次明确不做：

1. 自助注册
2. 多角色权限矩阵
3. 用户管理后台
4. 用户间文件转存
5. 协同编辑
6. 配额限制
7. 审计日志

## 推荐实施顺序

1. 补数据库字段和初始化数据
2. 放开登录限制并建立当前用户上下文
3. 为文件查询和文件操作补充 `user_id` 权限过滤
4. 为回收站、分享、统计补充权限过滤
5. 前端展示当前用户身份
6. 回归验证预览、上传、分享、回收站和统计

## 结论

这套方案足以把当前系统从“单管理员演示版”升级为“轻量多用户毕业设计版”。

它的优点是：

1. 改动集中，风险可控
2. 讲解清晰，答辩友好
3. 保留现有预览、转码、分享链路，不推倒重来
4. 工作量与毕业设计场景匹配，不会失控
